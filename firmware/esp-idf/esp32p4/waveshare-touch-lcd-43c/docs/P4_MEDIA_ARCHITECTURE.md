# ESP32-P4 媒体架构

本页面向微雪 4.3 英寸 P4 工程的二次开发，说明当前参与构建的模块、媒体所有权和性能边界。
编译、烧录见[开发板指南](../../../../../docs/boards/waveshare-esp32p4-touch-lcd-43c-v10/README.md)，
各业务参数统一维护在[音视频合同](../../../../../docs/product/MEDIA_CONTRACT.md)。

## 当前构建入口

工程的 `main/CMakeLists.txt` 引入仓库 `platforms/esp-idf/main/CMakeLists.txt`。
启动流程从共享 `app_main.c` 开始。以下路径均相对仓库根目录。

| 模块 | 职责 |
| --- | --- |
| `product/` | 平台无关的协议、会话和交互规则 |
| `platforms/esp-idf/components/starter_runtime/` | 产品状态、HTTP/MQTT 事件和媒体所有权交接 |
| `platforms/esp-idf/components/starter_tirtc/` | TiRTC 连接、订阅、收发和回调代次隔离 |
| `platforms/esp-idf/components/starter_product/` | LVGL 页面和用户操作 |
| `platforms/esp-idf/components/starter_media_common/` | 共享音频处理与 AEC |
| 本工程 `components/starter_media/` | P4 音频设备和媒体会话适配 |
| 本工程 `components/p4_hardware/p4_video.c` | 产品视频接口与 P4 管线衔接 |
| 本工程 `main/media/` | 摄像头编码管线、媒体档位和负载控制 |
| `platforms/esp-idf/waveshare_p4/` | 摄像头驱动、下行渲染、像素转换、缩放及内存策略 |
| `boards/waveshare/esp32p4-touch-lcd-43c/` | 板级接线与外设配置 |

`components/p4_hardware/CMakeLists.txt` 和共享 `component_sources.cmake` 列出实际媒体源文件。
修改前先核对注册项；旧 `main/application/`、`main/protocols/` 和 `main/ui/` 不代表当前产品入口。

## 会话与帧所有权

产品运行时决定何时进入 H5、AI、设备通话或微信通话。UI 只提交操作，不直接释放连接、
摄像头或播放器。异步回调须核对会话代次，上一轮的关闭事件不能作用于新会话。

摄像头帧由驱动借出，管线完成读取后归还。H.264 编码器输出完整 Annex-B 访问单元，
由媒体适配层发送。接收回调把压缩数据送入有界队列，解码、转换和显示分别推进，
不能在网络回调中执行整帧软件解码。

退出通话时先停止生产与投递，再清理队列、帧引用和连接。预热的固定工作区可以复用，
但会话状态与尚未显示的帧不能跨代保留。

## 摄像头上行

OV5647 输出完整 1280×960 YUV420 画面。H5 直接使用该尺寸硬件编码；设备互呼等比缩到
640×480，微信上行等比缩到 960×720。两种缩放都保留完整取景，不做中心裁切。

设备互呼以 5 fps 为当前基线。传感器模式标记的 45 fps 与网络发送帧率不同，应用按
目标节拍取帧。提高编码目标不能单独证明双向通话可提高帧率，还要测接收端解码与显示。
旋转提示属于各业务协议，不能把 H5 的角度直接套到微信或设备互呼。

上行档位由 `main/media/media_tuning.h` 定义，运行时由 `media_governor.c` 选择。
调整分辨率、帧率或码率时，同时更新能力上报、媒体合同和相应主机测试。

## 下行解码与显示

设备互呼接收 H.264，由 TinyH264 软件解码为 YUV420，再经 PPA 转为 RGB565。
当前使用单解码任务；双任务 helper 保留为实验配置，不能把它当作默认能力。

显示画布为 640×480，位于 800×480 横屏界面中，控件在前景显示。设备互呼采用
`contain`：默认 0°，按按钮依次旋转 90°、180°、270°，始终等比例完整显示。
640×480 输入在 0° 时不需要几何缩放，但仍需像素格式转换；90°/270° 时需缩放留边。

微信下行使用硬件 JPEG 解码。能力上报 `down_video_rotation=0`，两种呼叫方向均在
P4 本地使用 `cw90`，然后按 `cover` 映射到画布。微信的裁切策略与设备互呼不同，
不能为了修改设备互呼的取景范围而一并改变微信路径。

池配置集中在 `main/services/call_video_renderer_config.h`：

| 池 | 当前容量 | 用途 |
| --- | --- | --- |
| 压缩输入 | 24 × 256 KiB | 接收有界突发数据 |
| H.264 解码帧 | 4 × 460800 字节 | 保存不超过 640×480 的 YUV420 帧 |
| RGB565 输出 | 10 × 600 KiB | 转换与显示帧引用 |

输出池容量不等于固定播放延迟。自适应播放保留上限为 8 帧，实际深度看运行统计。
MJPEG 可直接丢弃过期帧；H.264 参考链损坏时需要新关键帧，不能任意丢压缩帧后继续解码。

## 内存和性能排查

大块图像和压缩数据放在 PSRAM；DMA 描述符、控制对象以及 cache-disabled 路径需要的
栈保留在内部 RAM。既要记录空闲总量，也要记录最大连续块，不能把“PSRAM 还有空间”
当作内部 DMA 分配一定成功的依据。

排查顺序是输入、解码、转换、显示。`VRX` 日志区分这些阶段的帧率、耗时、队列深度和
丢帧；`CAM` 日志记录采集、缩放、编码与发送。各阶段会并行执行，耗时不能直接相加
作为整机 CPU 占用率或端到端延迟。帧在本地队列中的年龄也不是摄像头到屏幕的总延迟。

当前双向视频的限制主要在软件解码和转换路径；5 fps 是产品基线，8 fps 尚未作为稳定
档位验收。历史测试和比较方法见
[P4 视频性能记录](../../../../../docs/product/P4_VIDEO_PERFORMANCE.md)。

## 修改后的验证

运行根目录 `bash tools/check.sh`，再按板卡指南构建。固件身份使用实际 ELF/BIN 的
SHA-256，不沿用旧文档中的版本、镜像大小或空闲分区数据。

实板回归至少覆盖两端互相发起设备通话、四个显示角度、微信双向发起、连续挂断重拨，
以及静态和持续运动画面。记录首帧、实际帧率、解码/转换耗时、丢帧和内存水位。
弱网恢复与长时间运行另行测试，构建通过不能代替这些结论。
