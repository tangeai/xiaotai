# BK7258 AI 对讲开发实践：用 Opus 补偿下行短时丢包

[中文](bk-opus-plc.md) · [English](bk-opus-plc.en.md)

AI 回复播放时偶尔缺一小段声音。开发时先确认哪里丢了音频，再用同一段语音在电脑上比较，最后上板听测。本例针对 TiRTC 送到 BK7258 的 16 kHz 单声道 Opus 语音，每包 20 ms。以下命令从包含本实现的仓库根目录运行。

## 1. 找到缺口和解码器

从 [TiRTC 接收回调](../../platforms/beken/runtime/src/xiaotai_tirtc.c)的 `on_audio` 跟到[播放线程](../../platforms/beken/runtime/src/xiaotai_audio.c)的 `playback_task`。对照同一流的媒体时间戳、到包时间和队列溢出计数。两个包隔了 60 ms 才到，但媒体时间戳只前进了 20 ms，说明这两个时间戳之间没有缺帧；此时补帧会拉长语音。

播放线程在 AP 核上调用 SDK 的 libopus 软件解码器。丢包隐藏（PLC）可用同一解码器的公开接口实现。带内前向纠错（FEC）允许后一个包携带前一帧的冗余信息，能否利用它取决于发送端。核对这两种调用后再设计模块。[Opus 解码接口](https://opus-codec.org/docs/opus_api-1.3.1/group__opus__decoder.html) · [RFC 7587 §3.3](https://www.rfc-editor.org/rfc/rfc7587.html#section-3.3)

## 2. 先在 PC 上做对照

在 Ubuntu 安装依赖，运行与固件共用同一份 C 实现的回放测试。其他主机可用 `OPUS_HEADERS` 指向含 `opus.h` 的目录，用 `OPUS_LIBRARY` 指向主机可加载的 libopus 文件。

```bash
sudo apt-get install build-essential libopus-dev python3
python3 tools/tests/test_bk_opus_plc.py
```

[测试入口](../../tools/tests/test_bk_opus_plc.py)读取仓库内男女声提示音，转为 16 kHz，编码后按固定种子丢弃整包。[回放程序](../../tests/audio/bk_opus_plc_replay.c)把同一组包送入三个独立解码器，分别得到无丢包参考、直接跳过丢包的基线和启用补偿的结果。在媒体时间线上对齐三者，每 5 ms 比较均方根响度。输出中的 `dropped` 是丢包数，`filled` 是补回帧数，`MAE` 是响度包络的平均绝对误差，越低越接近参考。

例如，女声随机丢 18/60 包，补回 10 帧，误差从 662.6 降到 471.3。验收时看男女声在随机、成簇两种 30% 丢包模型下的四组结果，并检查无丢包段逐样本一致、已补位置的迟到包不会重复播放。测试以 `OK` 结束。随 libopus 版本，具体误差可能变化。短提示音上的响度误差不能衡量整句可懂度。

## 3. 接入播放线程，限制每包开销

1. 入队时随包保存流 ID、轮次、媒体时间戳、接收时间和样本数。在播放线程出队后、写扬声器前调用[补偿模块](../../platforms/beken/runtime/src/xiaotai_opus_plc.c)。解码器和补偿状态由同一个播放线程持有。
2. 同流同轮先观察到两个连续的 20 ms 时间戳间隔。此后时间戳跳 40 ms 表示中间可能缺一帧，跳 60 ms 表示可能缺两帧。接收间隔超过 120 ms、切流、换轮次或静音抑制短包会打断判定。空队列时等待下一包。
3. 缺一帧时，用下一真包调用 `opus_decode`，令 `frame_size=320`、`decode_fec=1`。包中没有冗余时，库执行 PLC。缺两帧时，先用空包（数据指针为 NULL、长度为 0）补最早的 320 个样本，再处理最近的缺帧。最后以 `decode_fec=0` 正常解码同一真包。按时间顺序写出音频。
4. 16 kHz 下每帧 320 个样本，两帧补偿加当前帧刚好占满已有的 960 样本缓冲。正常包只解一次。沿用现有的扬声器和回声消除参考路径，避免额外线程及逐包内存分配。

30% 是设备**发送 Opus** 时的编码器预期丢包率。本例用 20 kbit/s、复杂度 3、带内 FEC 开启。默认 AI 上行是 A-law；要给 AI 下行增加冗余，需在服务端发送 Opus 的编码器上配置。接收端根据实际缺口调用公开解码接口，库按编码模式选择内部算法，无需直接调节 `silk_PLC`。[Opus 编码器参数](https://opus-codec.org/docs/opus_api-1.3.1/group__opus__encoderctls.html)

## 4. 在目标板验收，再决定是否移植

按[觅感双屏板指南](../boards/mgkfb-bk7258/README.md)准备工具链，从仓库根目录编译并按该指南烧录。另一款立创板要使用自己的板卡 ID 和镜像。[立创板指南](../boards/lckfb-bk7258/README.md)

```bash
python3 tools/build.py --board mgkfb-bk7258
```

用同一句 AI 回复分别跑无丢包和受控丢包。记录发送端丢弃的位置、设备播放阶段日志中的 `plc-ms`、队列溢出和解码耗时，录下扬声器输出。选定稳定语段，单独丢一帧或相邻两帧；下一包满足补偿条件且成功写出时，`plc-ms` 应分别增加 20 或 40。这个计数合并 FEC 和 PLC 时长。听句中是否断音、切轮时是否重复，同时测峰值 CPU 占用和播放线程栈余量。与相同条件下关闭补偿的基线比较。

本例已完成 PC 回放、两款 BK7258 构建及觅感双屏板烧录启动。真机弱网听感和峰值资源占用仍待测量。移植到其他设备时先检查 SDK 是否已代做补偿、时间戳单位、实际包长和输出缓冲容量，再用相同丢包位置重跑对照。TiRTC 此处没有发送包序号，发送端恰好停顿一两帧可能被误判；末尾丢包没有下一包可确认，更长的连续缺口也超出本例范围。

## 用 AI 协助复现

把目标板、SDK 版本、实际音频格式和上述测试入口交给 AI，分三次提问，每次用实际输出决定下一步。

- **查实现**：“从接收回调跟到扬声器，列出代码位置、时间戳单位、解码器归属和已有补偿。标出还缺哪项证据。”
- **做对照**：“用相同的编码包比较参考、跳包和补偿。输出丢包位置、已补时长及误差，解释一次补不回来的情况。”
- **上板验证**：“用目标板采样率重算最大输出样本数，指出接入点。根据这份串口日志和录音，列出已验证的现象及仍须实测的指标。”
