# 音视频链路诊断

build.74 起，ESP-IDF 公共 TiRTC 适配层提供固定容量、无媒体内容的统计。
该功能用于开发阶段定位等待发生在哪个边界；不改变音视频参数、重试策略、
socket 选项、任务优先级或队列容量。默认开机不采集，重启后需重新开启。

## 双机采集步骤

两台设备均烧录待比较固件，保留完整串口日志和 `status` 中的版本及 ELF 身份。
通话建立后，在两端执行：

```text
media-diag on
```

每隔约 10 秒，在两端执行以下命令，至少保留三个窗口：

```text
media-diag show
status
```

`show` 输出当前窗口并清零，下一窗口从本次输出开始；跨窗口仍未完成的调用
不会计入新窗口。`reset` 清空统计且保持开关状态；`on` 和 `off` 都清空统计。
结束后执行 `media-diag off`。仅命令输出汇总，不逐包打印。
每次新通话或切换单向/双向实验后执行 `reset`，避免混合不同实验。

构建选项 `CONFIG_STARTER_PIPELINE_DIAGNOSTICS=n` 可去掉统计与 socket 包装。
当前 P4 及两个 S3 项目均接入该选项；本轮实 SDK 编译验证为 P4。
运行时关闭时不读取计时器、不更新统计、不获取统计锁；编译开启仍有包装调用成本。

## 统计口径

| 行 | 耗时范围 | 间隔范围 |
| --- | --- | --- |
| `sdk-audio-submit` / `sdk-video-submit` | 调用 TiRTC 发送接口至返回 | 成功提交的调用开始时间 |
| `audio-callback` / `video-callback` | SDK 回调内执行应用媒体处理函数 | 应用处理函数入口时间 |
| `socket-send` / `socket-sendto` | lwIP 调用至返回 | 成功调用完成时间 |
| `socket-recv` / `socket-recvfrom` | lwIP 调用至返回，包含阻塞等待 | 成功调用完成时间 |

`call-us` 和 `gap-us` 均为微秒的平均值/最大值；`n` 包括失败调用，
`bytes` 仅累计成功字节，`fail` 为非零 SDK 返回值或负 socket 返回值的次数。
`last-error` 保留窗口内最后一次错误，socket 使用 errno；超时轮询错误不重置
成功事件间隔。socket 的成功零字节返回也计入事件。

socket 统计覆盖经这四个 lwIP 符号的所有业务，包含 MQTT/HTTP；未按 fd、
协议或 TiRTC 会话分流。它既不是 C6 无线收发统计，也不代表对端已经收到。
`recv` 的长耗时包含等待，不能直接解释为 CPU 占用。
回调统计从 SDK 交付到应用开始，不能拆出闭源 SDK 内部的组帧、重传与调度耗时。

`sdk-buffer` 来自既有发送缓存查询：`first/last/peak` 为采样缓存字节数，
`net-bytes-per-sec` 是首末采样之间的缓存净增长速率，正数为增长、负数为下降。
它不是网络吞吐量；采样峰值不代表未采样时刻的绝对峰值。

## 与既有日志结合判断

采集/转换/编码使用 `CAM`；下行解码、转换、显示使用 `VRX`；音频解码、
播放、接收间隔和溢出使用 `status`；P4 Hosted 接收交栈、发送入队与总线写入
使用 `[DEBUG-link71]`。这些已有统计各自保留原有窗口，需按串口时间对齐，
不要把不同窗口的计数直接相减。

- 摄像头稳定出帧而 SDK 提交耗时或缓存持续增长：继续检查发送排出边界。
- socket 有数据但媒体回调长时间不交付：进一步区分其他业务流量、SDK 组帧及调度。
- 回调持续交付而解码/转换/显示积压：检查设备处理阶段和内存争用。
- 音视频回调同时断续：结合两端 socket/Hosted 日志及抓包定位共同收发边界。

上述是排查方向，单个计数不能独立证明服务器、Wi-Fi、C6 或 P4 是根因。
本轮保留设备对讲上下行 640×480，需通过双机实测判断主要瓶颈。

## 回归验证

`tools/tests/test_pipeline_diag.py` 经生产发送入口及实际统计实现，检查默认关闭、
失败提交、跨 reset 的陈旧调用、并发累计、socket 返回值/errno/参数保留，以及
编译关闭路径。已经注册至 `bash tools/check.sh`。诊断使用固定存储，不记录
地址、凭据或媒体载荷；新处理阶段应接入公共统计接口并补实际入口回归测试。
