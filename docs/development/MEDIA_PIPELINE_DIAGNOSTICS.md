# 音视频链路诊断

## ESP UI 回调与屏幕刷新分开观测

ESP-IDF v5.5.5 下，`UI refresh slow` 是 100 ms 产品 tick 的墙钟耗时；
它包含抢占与等待，不是 CPU 独占时间，也不包含随后执行的 LVGL 屏幕渲染。
超过 20 ms 才报告，仍最多每 5 秒一次。新增 `stages-us`：

- `queue`：tick 入口到语音意图队列/提示处理结束。
- `runtime`：轻量运行状态快照；`product`：产品快照，含获取互斥锁的等待。
- `media`：媒体状态快照。
- `expression`：原有表情绘制计时。
- `view`：其余页面、文字、时钟和缓存更新；不包含上述阶段。

这些阶段之和等于 `total`，但任一阶段变慢仍可能来自任务抢占。
不能把 `expression=0` 的慢回调解释为嘴部绘制慢。

两个 S3 工程还安装 LVGL 8 `monitor_cb`，每约 5 秒汇总一行
`UI render window`。`refreshes` 是有脏区的刷新次数，`pixels` 是该窗口累计刷新
像素数，`max-pixels` 是单次最大值。320×240 全屏为 76800 像素；累计值允许超过
全屏大小，不能据此判断单帧全刷。

`render-ms` / `max-render-ms` 是累计/单次最大
渲染墙钟时间。当前 S3 PSRAM→SPI 驱动在 flush 内等待 DMA，因此包含这段同步传输，
但不是独立 SPI 总线计时。无脏区不触发回调，空闲时不强制刷新或打印。
这个统计由 LVGL 任务独占，不分配内存、不新增定时器、不更改绘制区域和媒体参数。
P4 不安装该回调，避免把不同显示驱动的完成语义混为一谈。

针对 M5 唱歌场景，保持同一会话、音量和距离，记录正常动画约 30 秒及
`voice-diag 10`，然后执行 `face-animation off`，再记录约 30 秒及 `voice-diag 10`。
最后执行 `face-animation on` 恢复。该开关只关闭播放波形嘴部动画，字幕、时钟与
情绪切换仍会刷新。按时间对齐 `UI render window`、分段慢回调及音频窗口的
`wall/audio-ms`、`capture-overflow`；不能用旧版日志与新版不同歌曲直接归因。

主机回归 `test_ui_refresh_observation.py` 验证计时边界和统计口径，不证明实板
卡顿已复现或解决。没有当前固件的对照日志，不能判定刷新面积、锁等待或调度谁是根因。

### 短时任务采样

当前 TiRTC 预编译 SDK 的 ABI 合同要求 `CONFIG_FREERTOS_USE_TRACE_FACILITY=n`，
不能直接启用 FreeRTOS 标准任务运行计数器。S3 的 `task-diag` 改用 ESP-IDF v5.5.5
官方 `esp_register_freertos_tick_hook_for_cpu`，在每核 tick 时观察当前任务句柄。
只在执行命令的 5 秒内注册 hook，结束或部分注册失败时注销，不更改内核配置。

输出按核列出采音/AEC、播放、上行编码、LVGL、产品 runtime、唤醒、摄像头及 idle。
这些任务从初始化后存活到复位；其他动态 SDK/网络任务统一计入 `other`。
缺失任务标为 `unavailable`。ISR 不读取 TCB 内容或任务名称，只在内部 RAM 的固定
数组中比较句柄并计数；短临界区保护启动、停止和两核采样，ISR 不打印或分配内存。

`share-permille=1000` 表示该核全部 tick 样本都观察到此任务，**不等于精确 CPU 时间**。
周期采样可能与任务周期重合，也会受关中断和中断归属影响；它不能直接量出单次 AEC
函数执行时间。每核 `total` 用于核对采样是否足够，零样本不能解释为 CPU 空闲。
采样本身有少量 ISR 开销，因此与此前日志对比时仍须保留固件版本身份。

命令只阻塞控制台任务 5 秒，音视频继续运行。空闲和持续播放时各采至少两次，结合
`voice-diag` 的墙钟时间与溢出判断任务分布。它用于选择下一处测量边界，不以一次
采样宣称某个库或任务是根因。P4/BK 未接入这个探针。

build.74 起，ESP-IDF 公共 TiRTC 适配层提供固定容量、无媒体内容的统计。
该功能用于开发阶段定位等待发生在哪个边界；不改变音视频参数、重试策略、
socket 选项、任务优先级或队列容量。默认开机不采集，重启后需重新开启。

## 双机采集步骤

两台设备均烧录待比较固件，保留完整串口日志和 `status` 中的版本及 ELF 身份。
通话建立后，在两端执行：

```text
media-diag on
```

每隔约 10 秒，在两端执行以下命令，至少保留三个窗口：

```text
media-diag show
status
```

`show` 输出当前窗口并清零，下一窗口从本次输出开始；跨窗口仍未完成的调用
不会计入新窗口。`reset` 清空统计且保持开关状态；`on` 和 `off` 都清空统计。
结束后执行 `media-diag off`。仅命令输出汇总，不逐包打印。
每次新通话或切换单向/双向实验后执行 `reset`，避免混合不同实验。

构建选项 `CONFIG_STARTER_PIPELINE_DIAGNOSTICS=n` 可去掉统计与 socket 包装。
当前 P4 及两个 S3 项目均接入该选项；本轮实 SDK 编译验证为 P4。
运行时关闭时不读取计时器、不更新统计、不获取统计锁；编译开启仍有包装调用成本。

## 统计口径

| 行 | 耗时范围 | 间隔范围 |
| --- | --- | --- |
| `sdk-audio-submit` / `sdk-video-submit` | 调用 TiRTC 发送接口至返回 | 成功提交的调用开始时间 |
| `audio-callback` / `video-callback` | SDK 回调内执行应用媒体处理函数 | 应用处理函数入口时间 |
| `socket-send` / `socket-sendto` / `socket-sendmsg` | lwIP 调用至返回 | 成功调用完成时间 |
| `socket-recv` / `socket-recvfrom` | lwIP 调用至返回，包含阻塞等待 | 成功调用完成时间 |

`call-us` 和 `gap-us` 均为微秒的平均值/最大值；`n` 包括失败调用，
`bytes` 仅累计成功字节，`fail` 为负 SDK 返回值或负 socket 返回值的次数。SDK 正数返回值表示成功发送字节数；
SDK 行的 `bytes` 累计成功提交的媒体载荷长度，可能不等于包含帧头的 SDK 返回字节数。
`last-error` 保留窗口内最后一次错误，socket 使用 errno；超时轮询错误不重置
成功事件间隔。socket 的成功零字节返回也计入事件。

socket 统计覆盖经这五个 lwIP 符号的所有业务，包含 MQTT/HTTP；未按 fd、
协议或 TiRTC 会话分流。它既不是 C6 无线收发统计，也不代表对端已经收到。
`recv` 的长耗时包含等待，不能直接解释为 CPU 占用。
回调统计从 SDK 交付到应用开始，不能拆出闭源 SDK 内部的组帧、重传与调度耗时。

`sdk-buffer` 来自既有发送缓存查询：`first/last/peak` 为采样缓存字节数，
`net-bytes-per-sec` 是首末采样之间的缓存净增长速率，正数为增长、负数为下降。
它不是网络吞吐量；采样峰值不代表未采样时刻的绝对峰值。

## 与既有日志结合判断

采集/转换/编码使用 `CAM`；下行解码、转换、显示使用 `VRX`；音频解码、
播放、接收间隔和溢出使用 `status`；P4 Hosted 接收交栈、发送入队与总线写入
使用 `[DEBUG-link71]`。这些已有统计各自保留原有窗口，需按串口时间对齐，
不要把不同窗口的计数直接相减。

- 摄像头稳定出帧而 SDK 提交耗时或缓存持续增长：继续检查发送排出边界。
- socket 有数据但媒体回调长时间不交付：进一步区分其他业务流量、SDK 组帧及调度。
- 回调持续交付而解码/转换/显示积压：检查设备处理阶段和内存争用。
- 音视频回调同时断续：结合两端 socket/Hosted 日志及抓包定位共同收发边界。

上述是排查方向，单个计数不能独立证明服务器、Wi-Fi、C6 或 P4 是根因。
本轮保留设备对讲上下行 640×480，需通过双机实测判断主要瓶颈。

## build.78 统计修正与调度复测

build.77 会将 SDK 正数成功返回误计为失败，且未观测 SDK 媒体发送使用的
`lwip_sendmsg`。旧日志中的“全部提交失败”和 sendto 零计数不能用于归责。
`recvfrom` 的 errno=11 通常表示非阻塞轮询暂无数据，不能直接作为丢包率。

P4 视频解码和转换在持续有帧时也执行至少一个 tick 的休眠，另按 500 ms
墙钟周期安排 5 ms 休眠；不再依赖每 30 帧一次的窗口。5 fps 下原周期约 6 秒，
已超过 5 秒看门狗间隔。保留看门狗、优先级、640×480、帧率和码率策略。
这是让出 CPU 的修复，不保证两个核的 IDLE 已实际运行，也不证明所有断流均来自调度。

实板需双向连续运动和语音至少 10 分钟，确认不再出现 IDLE1 看门狗，比较两端
音频溢出增量、视频回调间隔、转换耗时和输出帧率。采集每 10 秒一个诊断窗口；
仍有秒级回调缺口时结合新 `socket-sendmsg` 和双端收包观测继续区分 SDK/网络。

## build.79 单次通话对照：编码继续，只暂停提交

两端更新到同一 build.79，保持设备视频通话上下行 640×480，持续移动画面并说话。
测试期间不要使用界面关闭摄像头。`video-submit` 仅用于开发期 P4 设备呼叫，
由编码后的回调控制是否进入 SDK；不停止相机、编码器、音频或下行解码。
缺省 submitting，挂断或新连接时复位。运行时不要求 `media-diag` 已开启，
但编译必须包含 `CONFIG_STARTER_PIPELINE_DIAGNOSTICS`。

只在 A 端操作暂停；B 端保持正常发送。两端同时记录三个阶段，每阶段约 30 秒：

1. 正常双向：两端 `media-diag on`，30 秒后执行 `media-diag show`、`status`。
2. A 端 `video-submit pause`。等待 A 的 SDK 发送缓存接近零后，两端
   `media-diag reset`，再观察 30 秒；各执行 `media-diag show`、`status`，
   A 再执行 `video-submit show`。暂停不清空已有 SDK 缓存，旧包仍可能发送。
3. A 端 `video-submit resume`，等 `video-submit show` 变为 submitting，
   两端 `media-diag reset`，再观察 30 秒并输出相同统计。恢复等待自然关键帧，
   保证跳过的视频参考帧不会使接收端从非关键帧继续解码。GOP=10、5 fps 时
   通常等待不超过一个 GOP，但调度或编码异常时不能保证。

暂停阶段验收：A 的 CAM 帧率、编码耗时仍持续输出；skipped 递增；
SDK video-submit 计数不再增长，p4_video tx 不增加、tx-fail 不增加。
B 不再接收 A 新视频是预期现象；重点观察 A 接收 B 的音视频及双向声音。
恢复后对比第三阶段是否再次恶化；码率反馈仍按原策略工作，注意实际码率差异。

若暂停提交后改善，说明减少提交后的 SDK 工作/拷贝与链路流量有效，
不能单独证明无线丢包；若暂停提交仍卡而真正关闭相机才改善，
优先进一步检查采集、编码与资源竞争。单次对照不构成硬件能力或 SDK 根因证明。

### build.80：SDIO 双向总线等待优化

只改变 P4 SDIO TX 缓冲轮询时的锁范围：C6 暂无接收额度时，原有后半轮询的
1 ms 休眠释放总线锁，醒来重新取得锁后查询寄存器。实际 CMD53 写入、额度
缓存/消耗及原有重试、失败处理保持不变。只有一个 TX 消费线程，RX 不消费
TX 缓存额度。原先一次额度耗尽最多有 25 次持锁休眠，可能推迟下行数据及
确认包的读取；消除此阻塞并不证明无线空口或 SDK 重传已正常。

本轮不使用暂停命令：两端刷 build.80，正常开启双方摄像头通话约两分钟，
观察是否仍有数秒冻结。若卡顿，保留发生前后的 `p4_video`、`VRX` 和一次
`status`；与 build.79 同网络、同场景比较。上下行仍为 640×480，其他媒体
及 Wi-Fi 配置保持原值。主机回归与编译通过不替代此次实板比较。

### build.82：板卡与实际传输探针

先联网、保持空闲，在控制台输入一次 `board-probe`，再正常发起视频通话。

读取变参前丢弃，不输出源路径、opaque handle 或 SDK 原文。不启用 STAT。
当前以 NOTICE 级别维持白名单钩子，便于重连自动观测；仍可能有 SDK 端日志
分支开销，不能把该诊断版与关闭探针版当作严格同开销性能对照。

`poll_segments` 是每次 poll 的最大发送分段数；`interval_ms` 是 KCP 更新
间隔；`sndcap` 是缓存容量。没有 TP 日志表示未确认，不能从 SDK 版本或
业务 mode=4 推定传输协议。SDK 升级后需重新核对日志模板。

身份探针结果回来后再决定 Hosted/C6 迁移；上下行 640×480 保持用户基线。

## CoreS3 持续对话采音观测

适用工具链：ESP-IDF **v5.5.5**。CoreS3 build.15 增加只读关联观测，
不调整 AEC、音量、麦克风增益、采样率、DMA 容量或任务优先级。
这是一版诊断固件，不表示重复说话或双讲问题已经修复。

进入 AI 对话后执行 `voice-diag 30`，在这 30 秒内正常提问、等待回复，
并在回复期间尝试说一句话。无需记忆秒数或刻意重复唤醒词。
命令结束后执行 `status`，保留从 Firmware 身份到两个命令结束的完整输出。
`voice-diag` 不录制 PCM，不打印识别文本或凭证。

新 `Audio window` 与紧邻的 `Voice levels` 使用同一个窗口 ID，包含 32 个
成功 AEC 块，即当前 16 kHz / 512 样本配置下的 1024 ms 音频。
相同 ID 重复打印表示尚无新完整窗口，不能重复计数。字段含义：

| 字段 | 含义 |
| --- | --- |
| `read-ms`、`wall/audio-ms` | 第一块读取开始至最后一块读取结束的墙钟区间、累计处理音频时长；不是 ADC 硬件时间戳 |
| `worker/dma-frames` | 32 块中，在读取前或后观察到播放 worker 活动、估算 DMA 尾音非零的块数；两项可能重叠 |
| `pending-peak` | 读取边界采样得到的待播数量峰值，含 worker 持有槽；排队不等于已出声 |
| `dma-tail-max-ms` | 已有播放时序模型估算的最大尾音余量；是保守边界，不是实测 DMA 填充量 |
| `clipped-mic/ref` | 该窗口接近满量程的样本数，阈值沿用 ±32700；与整机累计数分开 |
| `tx/rx/drop` | 相同读取区间内应用成功发送、下行入队、应用丢弃计数的增量；不证明服务器收到或识别 |
| `capture-overflow` | CoreS3 I2S RX 驱动队列溢出事件增量，不等于丢失 PCM 样本数 |

CoreS3 通过 IDF 的 `on_recv_q_ovf` 回调只计数，不在中断中打印或做音频处理。
依据锁定版本的 [I2S 实现](https://github.com/espressif/esp-idf/blob/b774170ff46c393eeb5e495ea37936038d3f4f4f/components/esp_driver_i2s/i2s_common.c)：
队列满时移除旧条目并触发回调。观测注册在通道初始化后、codec 启用之前。
立创 S3 复用窗口统计，但未接入该硬件回调时显示 `unknown`；P4 未提供关联窗口，
显示 `unavailable`。不能把未提供观测解释为没有溢出。

会话代次、模式、激活状态变化会丢弃未完成的观测窗口，不改变实际采音和发送。
会话计数清零与代次更新交错时，增量标记为 unknown，避免整数下溢制造巨量丢包。
这些只是读取边界采样，不能识别是谁在说话，也不能为已经积压的 PCM 还原采集时刻。

命令开始、结束会各打印已有的最多 8 条运行时事件。`ASR caption final`
表示收到服务端用户最终识别字幕；`AI caption final` 表示 AI 最终字幕。
它们是固定事件标签，没有对话原文；历史容量有限，早期事件可能被淘汰。
事件时刻和读取区间共用设备单调时钟，用于缩小排查范围，不能代替声学听音验证。

### ESP UI 周期任务的范围

产品状态仍以 100 ms 刷新，但常规 UI 和输入处理使用 `starter_runtime_status_snapshot()`，
只读原子状态，不再逐次扫描 FreeRTOS 栈水位；控制台 `status` 和诊断页仍按需测量。
P4 的 30 ms 显示 timer 初始暂停，只在通话页且视频 owner 已就绪时运行；
语音通话、AI、待机和 H5 首页不运行该显示轮询。离开视频或挂断时做一次显示清理。
这项优化去除可确认的重复工作，不代表实板 `UI refresh slow` 或 AEC 超期已经消失。
