TiRTC ESP32-P4 双向 VGA 视频通话：发送积压与接收完整帧长间隔
整理日期：2026-10-11

一、环境与复现
设备：ESP32-P4 + ESP32-C6，ESP-Hosted SDIO，4 线 40 MHz。
SDK：启动日志报告 TiRTC v2.5.0-9088239c，tgtrp v1.5.18-f72f5d3c。
ESP-IDF：本地 build.80 描述符 v5.5.4-dirty。
业务：设备对设备 mode=4，双方 H264 640×480，上行目标 5 fps、GOP10，
初始配置 600 kbps，SDK 建议经本地策略调整，允许范围 150～600 kbps。
视频流号 11；音频保持双向；SDK 配置发送缓冲 2097152 字节。
用户报告关闭一端摄像头后改善。症状为双向视频期间画面数秒停顿、音频间断。

最近硬件日志身份：1.0.0+build.80，ELF 前缀 1f592970a。
完整 ELF SHA256：1f592970a46cd496fee30eb66e48cd93d862151fe8d7602c96e909a1c5615287
应用 BIN SHA256：bf70edd66891d216146a34bc3d95f63e22aad097f205d643547289bcb8d11493

二、关键证据（原始节选见同目录 sdk-evidence.log）
1. build.80，40.132～45.144 秒：应用视频成功提交数 tx=24→49，而视频
接收数 rx=8→9；SDK 缓冲占用 208367→234642 字节。
2. 同次通话出现 input_gap=4.438、8.571、5.668 秒，对应单帧解码耗时
约 98、72、133 ms。应用日志标记 stage=input。
这些 input_gap 是应用接收/解码入口的观测，单独不能证明 SDK 内部卡住；
但此前独立统计也记录 SDK 视频回调间隔超过 7 秒。
3. 相机采集、编码通常保持 5 fps，编码约 7～9 ms。
4. SDK 连续建议降码率：510→255→204→163.2→150 kbps，期间有 I 帧请求。
成功提交、成功写入 SDIO 或 socket，并不代表无线送达或对端解码成功。
5. build.80 状态音频 rx-overflow=253，为该会话累计值，不是单窗口丢包率。

三、最有区分力的对照
build.79 在同一通话执行 video-submit pause：仅停止本机编码帧提交 SDK，
相机与编码器、音频及下行继续运行。
观察：tx 固定为 268，缓存排空到接近 0，下行输入连续约 4.9～5.0 fps，
从 92.515 秒到 147.900 秒的节选中没有此前数秒级停顿告警。
CAM 仍约 5 fps，编码仍约 8 ms。
恢复双向发送的后续新通话再次出现约 9.4 秒、8.7 秒输入间隔。
限制：后续为重新建连，不是同一通话内 resume，存在网络/场景变化；暂停
同时减少 SDK 调用、内存复制和传输负载，不能据此只归责无线或 SDK。
暂停通话末尾 connection error=-40008，请 SDK 方解释该错误的准确含义；
当前不自行认定为某种超时，亦不认定其由暂停导致。

四、已有分段统计
build.78 独立 18.012 秒窗口：
音频提交 901 次，平均 238 us，失败 0，平均间隔约 20 ms。
视频提交 90 次，平均 441 us，失败 0，平均间隔约 200 ms。
视频回调 23 次，最大间隔 7.089 秒；回调自身最大耗时 314 us。
全 lwIP recvfrom 成功包间隔最大约 224 ms，socket-sendmsg 成功写入
2086028 字节，同窗口应用提交音视频共 552758 字节。
口径限制：socket 统计覆盖所有 lwIP 流量，不限定 TiRTC 连接，不等于纯媒体
流量。额外字节可能来自重传、协议开销和其他连接，不能直接算重传率。
recvfrom last-error=11 可为非阻塞 EAGAIN，不代表空口丢包。
更早存在 SDK 正数返回值被误记失败的统计，未纳入本反馈。

五、应用侧已处理与尚存问题
Wi-Fi 省电已关闭；SDIO 已采用 streaming，缓冲/聚合配置已有扩容。
build.80 将 SDIO TX 等待 C6 空闲额度时的 1 ms 休眠移到总线锁外，主机
回归和编译通过，用户同版硬件日志仍显示秒级卡顿，未证明该处为主因。
rtc_thread 原 8 KiB 栈曾在 sprintf/_svfprintf_r 栈保护异常；现最小 24 KiB。
该历史崩溃与当前断流分别跟踪，不把未再崩溃当作稳定性证明。
显示转换仍偏慢，可限制显示到约 4 fps；另有自适应播放缓冲等待，放大了
可见停顿。它们不能单独解释 SDK 视频回调 7 秒无完整帧的现象。
