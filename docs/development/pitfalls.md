# 二次开发易错点与回归入口

修改界面、音频队列或会话退出流程前，先核对这里的约束。每项同时保留生产代码入口、
可运行的回归测试和实板验证范围。主机测试通过不能代替板级触摸、DMA 或实际听音验收。

## 房间数字键不能与普通按钮共用操作编号

**症状**：输入房间号时，“1”无反应、“9”显示星号、“0”进入密码页、“删除”无效，
“2”进入退出确认。这类固定按键触发固定错误操作的问题，应先检查动作编号，再检查触摸坐标。

**原因与约束**：[ESP 界面适配器](../../platforms/esp-idf/components/starter_product/src/starter_product.c)
的普通动作采用递增枚举，数字键采用基址加数字。旧数字基址为 40，新增普通动作后发生重叠：
数字 0 与设置密码重叠，数字 1 与加入房间重叠，数字 2 与退出房间重叠；删除等操作也落入数字范围。
当前数字范围为 80–89，退出确认等操作为 60–63，联系人从 100 开始。
新增动作必须保留范围隔离，并保留枚举后的 `_Static_assert` 编译检查。

**测试方式**：必须使用生产枚举，捕获实际渲染按钮的编号再交给生产动作分发代码。
在测试中手写一套互不重叠的编号会掩盖此缺陷。现有测试覆盖 0–9、空输入删除、
6 位房间号、4 位密码、密码掩码、无密码加入、创建和退出确认。

```bash
python3 tools/tests/test_room_keypad.py
```

**验证范围**：2026-10-09，Waveshare ESP32-P4 4.3 英寸板，`1.0.0+build.34`
完整构建和全量检查通过；用户烧录后确认操作恢复正常。代码由 ESP 平台界面共用，
该结论不等于 S3 或 BK 的触摸实板验收。

## 重新加入房间必须初始化本次租约

**症状**：创建、退出后再次创建房间，刚进入 `room-active` 就出现
`room lease expired locally` 并断开。网络连接与媒体首帧都成功，不代表租约状态正确。

**约束**：ESP 适配器退出房间时清零下一次续期时间和租约截止时间；接受新一轮
`join_room` 成功回复时，在提交 presence HTTP 前初始化本次租约和续期时间。
不能依赖异步 HTTP 成功回复才初始化，否则旧租约已过期时，新连接会在回复到达前被关闭。
重复 join 回复不能重新延长租约，旧代次回复和无效媒体格式也不能启动租约。
BK 使用独立的公共房间状态机，不能据此把其 IPC 心跳重启归为同一根因。

```bash
python3 tools/tests/test_room_lease_lifecycle.py
```

回归测试重放实际 ESP 加入回调和退出代码，覆盖连续五轮加入/退出、续期 HTTP 延迟、
重复回复、旧代次回复和无效回复。主机验证通过，重复创建的实板验收仍待完成。

## 顶层提示条必须按其父层居中

**症状**：“手动启动”等提示条在大屏上偏向一侧。

**约束**：普通页面布局的横向偏移不能直接用于 `lv_layer_top()` 上的提示条。
提示文字居中与提示条本身居中是两件事：文字使用居中样式，提示条按父层宽度对齐。
当前 ESP 界面使用 `LV_ALIGN_TOP_MID`，纵向距离按屏幕高度缩放。

```bash
python3 tools/tests/test_tip_layout.py
```

测试在 320×240、480×320 和 800×480 布局边界验证文字及提示条位置。
更换显示布局后仍需实机检查遮挡、旋转和触摸区域。

## AI 音频须容纳突发下发，并排空尾音后退出

**症状**：开头听感异常或漏字；字幕显示完整结束语，但只听到前几个字就退出。

**约束**：网络包到达节奏不等于扬声器播放节奏。AI 队列应容纳突发音频，不能照搬
实时通话的小队列，也不能通过加快播放清空积压。P4 当前 AI 接收队列为 64 槽，
非 AI 实时音频保持独立的积压限制；BK 的 Opus 队列也扩至 64 槽。
容量仍是有限的，不能宣称消除了所有弱网或超容量丢包。

服务端 `end_session` 与传输关闭都不能直接丢弃已接收的下行音频。
退出判断必须覆盖接收队列、解码/写入中的帧和板级播放尾部；“队列空”不等于“扬声器已播完”。
BK 从队列取走最后一个包时就要标记播放中，解码失败也必须释放该标记，避免退出竞态或永久等待。
具体到达窗口和等待上限遵守[交互合同](../product/PRODUCT_INTERACTION_PROFILES.md)
及[交互适配说明](../../product/interaction/README.md)。

```bash
python3 tools/tests/test_p4_ai_playback.py
python3 tools/tests/test_bk_ai_playback.py
python3 tools/tests/test_bk_disconnect_playback.py
```

排查时同时记录接收、解码、写入帧数、overflow、pending、active、PCM 时长、DMA/播放尾部
和最后接收时间；比较 `end-session`、`transport-close`、`drained` 三阶段。
累计 PCM 时长与整个会话耗时的差值包含对话空白，不能直接判定播放加速；写入成功也不等于
已验证扬声器实际声音。设备只能排空收到的包，不能补播服务端尚未发送就关闭的音频。

**已有证据**：P4 `build.31` 的日志出现接收溢出 83 次；`build.33` 的后续日志中
994 帧全部接收、解码和写入，溢出为 0，等待播放排空后才回到等待态，用户确认原症状消失。
另一轮 1616 帧也完成排空。BK `build.9` 的回归测试及构建通过，仍待 BK 实板听音验证。
S3 使用自己的媒体实现，不能仅因共享 runtime 或已有 64 槽队列就判定同步修复完成。

**BK 远端关闭的新增证据**：2026-10-09 提供的日志在 `end-session` 记录
`rx=349 written=303 pending=45 active=1 overflow=0`，但断开后仅写入 305 帧。
媒体工作线程在处理断开请求时先调用 `xiaotai_audio_stop()`，清空了剩余音频；
后续关闭事件才检查排空，因此 `pending=0` 和“drained”不能证明尾音已播完。

远端 AI 错误断开现在先关闭上行、等待播放排空（最多 3 秒），再停止并回收音频，
最后调用 `TiRtcDisconnect()`。停止并等待采集线程退出仍须早于 SDK 释放连接。
用户主动挂断和实时通话退出保持立即停止，旧连接清理不能操作当前音频。
新增回归重放实际媒体工作线程断开分支，覆盖日志中的尾音、播放卡住、主动退出和旧连接；
主机验证通过，扬声器尾音仍待本次固件实板验证。

房间退出后的 AP 心跳失联重启尚未证明根因。多次日志在扬声器关闭、RTC socket 9
关闭后，未出现 `connection closed`，随后 CP 报 8 秒心跳超时并断言。
正常退出也会出现 `Task exits abnormally!`；固定 SDK 的该分支记录任务函数返回，
随后调用 `vTaskDelete(NULL)`，这条日志本身不能证明死锁。
连接回收增加 `TiRtcDisconnect begin`、`returned` 和 `disconnected callback`
边界日志，下一轮需保留退出到重启全过程及固件版本，区分 SDK 调用、回调和产品关闭事件。

2026-10-09 后续带边界日志的实板记录：14:19:14，AI 远端关闭时剩余 29 个包及
一个播放中帧，等待 760 ms 后 `rx=2433 written=2433 overflow=0 pending=0 active=0`
且播放尾部为 0，再停止音频。这证明该轮已收到的 AI 音频完成写入和播放尾部等待，
听感仍以用户确认为准。

14:08:41 的房间退出完成后持续 READY 约 8 分钟；
14:19:37 的下一轮房间退出却在 `TiRTC disconnected callback` 入口之后停止输出，
14:19:52 心跳断言重启，未出现关闭事件处理完成日志。
该轮停在回调入口到工作线程完成关闭之间，并非已证明 SDK 断开调用阻塞。

14:38:33 的后续复现停得更早：麦克风任务退出完成，但扬声器停在
`spk_data_read_task_deinit`，没有出现退出完成、`audio stopped` 或
`TiRtcDisconnect begin`；14:38:48 心跳断言重启。固定 SDK 在此发送退出消息、
中止 ringbuffer 后无限等待任务的退出信号。仅凭现有日志无法区分队列发送、
任务退出及资源释放中的具体阻塞点，也不能把所有复现归到 RTC 回调。

诊断版本用临时 `[DEBUG-bk-close]` 标记状态清理、队列投递和工作线程各阶段；

`TiRtcDisconnect` 返回后出现 `connection error=-40008`，随后停止输出并断言。
因此不能把此前最后一条扬声器日志当作所有复现的根因。

## 断开原因与其他告警必须保留证据边界

ICE 心跳发送日志本身不表示超时；看到后续 timeout/failed 才能确认此次心跳失败。
传输错误不能仅凭通用返回码写成“服务端空闲超时”，应结合结束命令和心跳日志。
正常 AI 结束时出现关闭回调，也不能据此判定尾音丢失，必须看最终排空统计。

铃声切换到实时通话时的 `amp=0` 播放阻塞，以及唤醒后的 preroll/replay 中断，属于不同路径；
当前对话日志只提供了告警证据，没有完成独立复现与修复验证，不能列为已修复事项。

## BK 多人对讲松手必须可靠送达

`ROOM TALK` 日志不能单独证明整机死锁。BK 触摸释放原先可能在控制队列满时丢弃；
触摸驱动也只等中断，漏掉松手中断后不会继续读控制器。这两个缺陷已有失败回放。
释放代次现在独立于有界队列保存，由控制任务发出停止 intent；按住期间每 20 ms
读取真实硬件状态，释放后恢复中断等待。不得把软件队列为空或按住时长作为松手依据。

入口为 `touch_event`、`service_room_touch_release` 和 SDK `tp_process_task`；
回归运行 `tools/tests/test_bk_ptt_release_delivery.py`、
`tools/tests/test_bk_touch_release_poll.py`，均登记到 `tools/check.sh`。
build.21 编译通过；用户此次实板卡住的具体触发路径尚未确认，仍需验证长按、快速连按、
移出按钮松手及平台通知并发时能关闭上行，且无心跳超时或重启。

## 后续维护

新增条目应包含症状、根因或尚待证明的假设、必须保持的约束、生产入口、回归命令和验证范围。

### ESP32：平台解绑不能在 PSRAM 任务栈直接擦除 NVS

平台 `unbind` 在 `starter_session` 会话任务中处理；其 24 KiB 栈位于 PSRAM。
ESP-IDF 擦写 Flash 时可能关闭缓存，若直接调用 NVS 擦除，会在
`spi_flash_disable_interrupts_caches_and_other_cpu` 触发
`esp_task_stack_is_sane_cache_disabled()` 断言，随后设备停止运行，屏幕可能白屏。
这是任务栈的内存能力限制，不能通过增大 PSRAM 栈或屏蔽断言解决。

共用 `runtime_config_clear_tirtc()` 对 PSRAM 栈调用者使用临时内部 RAM 栈任务，
同步等待擦除与提交完成后才返回；内部 RAM 栈调用者直接执行。只清除 TiRTC
凭证命名空间，保留 Wi-Fi 和产品设置。任务创建失败、擦除失败、提交失败必须返回
错误；不能把请求已提交当作擦除完成。回归：
`python3 tools/tests/test_unbind_flash_stack.py`，已接入 `tools/check.sh`。
主机边界回放不代替 P4/S3 实板解绑验收：需在 AI/通话中及空闲时解绑，确认无断言，
重启后停留绑定页，网络设置保留，重新绑定可恢复使用。

### 绑定 ACK 已到达，仍等待三次验证码语音

ESP 共用组合根在绑定工作任务同步播报三次；临时 MQTT 已确认绑定 ACK，工作任务
仍等待语音返回，用户日志出现约 14 秒额外延迟。重绑随后受控重启，又表现为无提示闪屏。
绑定配置现在提供非阻塞取消回调，在匹配的 ACK 确认时调用现有 PCM 取消机制；
三次播报共用播放 epoch，并在每次播放前、返回后及短间隔中检查取消标志。
保存凭证成功后再向 UI 投递“绑定成功，正在启动…”，ESP 重绑预留 1 秒显示时间。
BK 原有独立播报任务保留，缩短间隔中的取消等待，并把成功提示移到存储成功之后。

`tools/tests/test_binding_completion.py` 重放实际播放、ACK 分支和保存入口，覆盖提前确认、
播放中确认、间隔确认、非匹配 ACK、无取消回调及保存失败；绑定布局回归覆盖成功提示。
完整主机检查与 BK 合同通过；P4 build.46、S3 build.34、BK build.27 编译通过。
尚待三板实测播报中途完成绑定后的停声、成功提示、重绑重启及再次上线。
