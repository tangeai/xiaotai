# 二次开发易错点与回归入口

修改界面、音频队列或会话退出流程前，先核对这里的约束。每项同时保留生产代码入口、
可运行的回归测试和实板验证范围。主机测试通过不能代替板级触摸、DMA 或实际听音验收。

## 房间数字键不能与普通按钮共用操作编号

**症状**：输入房间号时，“1”无反应、“9”显示星号、“0”进入密码页、“删除”无效，
“2”进入退出确认。这类固定按键触发固定错误操作的问题，应先检查动作编号，再检查触摸坐标。

**原因与约束**：[ESP 界面适配器](../../platforms/esp-idf/components/starter_product/src/starter_product.c)
的普通动作采用递增枚举，数字键采用基址加数字。旧数字基址为 40，新增普通动作后发生重叠：
数字 0 与设置密码重叠，数字 1 与加入房间重叠，数字 2 与退出房间重叠；删除等操作也落入数字范围。
当前数字范围为 80–89，退出确认等操作为 60–63，联系人从 100 开始。
新增动作必须保留范围隔离，并保留枚举后的 `_Static_assert` 编译检查。

**测试方式**：必须使用生产枚举，捕获实际渲染按钮的编号再交给生产动作分发代码。
在测试中手写一套互不重叠的编号会掩盖此缺陷。现有测试覆盖 0–9、空输入删除、
6 位房间号、4 位密码、密码掩码、无密码加入、创建和退出确认。

```bash
python3 tools/tests/test_room_keypad.py
```

**验证范围**：2026-10-09，Waveshare ESP32-P4 4.3 英寸板，`1.0.0+build.34`
完整构建和全量检查通过；用户烧录后确认操作恢复正常。代码由 ESP 平台界面共用，
该结论不等于 S3 或 BK 的触摸实板验收。

## 顶层提示条必须按其父层居中

**症状**：“手动启动”等提示条在大屏上偏向一侧。

**约束**：普通页面布局的横向偏移不能直接用于 `lv_layer_top()` 上的提示条。
提示文字居中与提示条本身居中是两件事：文字使用居中样式，提示条按父层宽度对齐。
当前 ESP 界面使用 `LV_ALIGN_TOP_MID`，纵向距离按屏幕高度缩放。

```bash
python3 tools/tests/test_tip_layout.py
```

测试在 320×240、480×320 和 800×480 布局边界验证文字及提示条位置。
更换显示布局后仍需实机检查遮挡、旋转和触摸区域。

## AI 音频须容纳突发下发，并排空尾音后退出

**症状**：开头听感异常或漏字；字幕显示完整结束语，但只听到前几个字就退出。

**约束**：网络包到达节奏不等于扬声器播放节奏。AI 队列应容纳突发音频，不能照搬
实时通话的小队列，也不能通过加快播放清空积压。P4 当前 AI 接收队列为 64 槽，
非 AI 实时音频保持独立的积压限制；BK 的 Opus 队列也扩至 64 槽。
容量仍是有限的，不能宣称消除了所有弱网或超容量丢包。

服务端 `end_session` 与传输关闭都不能直接丢弃已接收的下行音频。
退出判断必须覆盖接收队列、解码/写入中的帧和板级播放尾部；“队列空”不等于“扬声器已播完”。
BK 从队列取走最后一个包时就要标记播放中，解码失败也必须释放该标记，避免退出竞态或永久等待。
具体到达窗口和等待上限遵守[交互合同](../product/PRODUCT_INTERACTION_PROFILES.md)
及[交互适配说明](../../product/interaction/README.md)。

```bash
python3 tools/tests/test_p4_ai_playback.py
python3 tools/tests/test_bk_ai_playback.py
```

排查时同时记录接收、解码、写入帧数、overflow、pending、active、PCM 时长、DMA/播放尾部
和最后接收时间；比较 `end-session`、`transport-close`、`drained` 三阶段。
累计 PCM 时长与整个会话耗时的差值包含对话空白，不能直接判定播放加速；写入成功也不等于
已验证扬声器实际声音。设备只能排空收到的包，不能补播服务端尚未发送就关闭的音频。

**已有证据**：P4 `build.31` 的日志出现接收溢出 83 次；`build.33` 的后续日志中
994 帧全部接收、解码和写入，溢出为 0，等待播放排空后才回到等待态，用户确认原症状消失。
另一轮 1616 帧也完成排空。BK `build.9` 的回归测试及构建通过，仍待 BK 实板听音验证。
S3 使用自己的媒体实现，不能仅因共享 runtime 或已有 64 槽队列就判定同步修复完成。

## 断开原因与其他告警必须保留证据边界

ICE 心跳发送日志本身不表示超时；看到后续 timeout/failed 才能确认此次心跳失败。
传输错误不能仅凭通用返回码写成“服务端空闲超时”，应结合结束命令和心跳日志。
正常 AI 结束时出现关闭回调，也不能据此判定尾音丢失，必须看最终排空统计。

铃声切换到实时通话时的 `amp=0` 播放阻塞，以及唤醒后的 preroll/replay 中断，属于不同路径；
当前对话日志只提供了告警证据，没有完成独立复现与修复验证，不能列为已修复事项。

## 后续维护

新增条目应包含症状、根因或尚待证明的假设、必须保持的约束、生产入口、回归命令和验证范围。
修复时先看到回归测试失败，再修改代码；测试统一登记到 `tools/check.sh`。
不要只留下聊天结论，也不要把单块板的验证推广到所有 SDK 和板卡。
