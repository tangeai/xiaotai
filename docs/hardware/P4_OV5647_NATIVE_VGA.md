# P4 OV5647 原生 VGA 采集实验（build.72）

本文是旧版原生 VGA 实验记录，不是当前采集配置。build.98/99 的实板仍观察到
彩边，当前 `APP_MEDIA_CALL_NATIVE_VGA_CAPTURE_ENABLE=0`；设备互呼和微信 VoIP
继续从 1280×960 全幅采集后缩小。后续章节中的“当前”“本轮”仅指当时实验。

build.71 的双端日志显示：关闭本机摄像头后，下行转换平均耗时从约 141ms 降至
51～74ms，重新开启后回升。该对照支持并发资源竞争，尚不能单独区分 CPU、PPA、
内存带宽和无线负载，也不能证明下述修改已经消除声音或视频卡顿。

## 参考与适配边界

- 乐鑫 `esp-video-components` 的 `video_custom_format` 示例通过
  `VIDIOC_S_SENSOR_FMT` 配置自定义传感器格式，再协商采集像素格式。
  本项目已有对应接口，OV5647 `set_format` 接受外部格式表，保持指针引用。
  参考：<https://github.com/espressif/esp-video-components/tree/master/esp_video/examples/video_custom_format>。
- 截至 2026-10-11 检索到的乐鑫 OV5647 驱动未提供可直接复用的 VGA 模式；
  上游还有缺少 VGA 模式的议题：
  <https://github.com/espressif/esp-video-components/issues/30>。
- Linux OV5647 驱动存在全视野 VGA 的传感器合并像素和抽样模式：
  <https://github.com/torvalds/linux/blob/master/drivers/media/i2c/ov5647.c>。
  本实现参考其 VGA 抽样寄存器含义，不复制 Linux 驱动实现或直接照搬其时钟配置。

新增平台内 `ov5647_vga_capture.h`：基于当前锁定的乐鑫 24MHz RAW10
1280×960/45fps 模式复制寄存器表，输出尺寸改为 640×480，抽样步进改为
0x35，补充 VGA 采样控制。保留当前 PLL、MIPI 时序、方向与传感器窗口。
自定义 ISP 的 HTS/VTS 分别为 1796/1093，与寄存器 0x380c-f 对齐；原模式元数据
两者颠倒，本轮只修正新模式的副本。全部表使用静态存储，满足驱动引用生命周期。
这是一项待实板验证的组合，不等同于乐鑫已经验证过的 VGA 模式。

## 行为变化

- 设备视频对讲：640×480、5fps、600kbps；微信视频：640×480、8fps、500kbps。
  应用发送参数不变；采集目标改为原生 VGA，通过已有 `yuv420-direct` 编码路径。
- 传感器时钟和标称 45fps 保留，应用按 5/8fps 取帧；没有宣称传感器本身降至
  5/8fps。本轮旨在缩小 CSI/ISP 帧尺寸并绕过上行 PPA 缩放。
- H5 仍为 1280×960、20fps、3Mbps，采用原模式。非 VGA 采集走已有格式协商。
- 不旋转上行像素；接收显示方向、音频、队列容量、优先级与拥塞策略不变。
- VGA 格式协商失败时返回错误，不冒充原生采集成功；无需缩放器时预热直接成功，
  避免阻断视频初始化。没有修改或复制整个 managed component。

## 验证与烧录验收

主机测试 `tools/tests/test_p4_native_vga.py` 编译生产格式协商代码，覆盖原生尺寸、
寄存器副本、持久引用、重启、非 VGA 场景、未知源模式和 ioctl 失败。
`test_full_frame_uplink.py` 经公开策略入口验证设备/微信原生采集及 H5 原参数。
测试按修改前失败、修改后通过执行，并注册 `tools/check.sh`。

本机没有串口设备；本轮没有烧录，也没有证明实板出图或性能改善。两台 P4 烧录
相同版本后依次验证：

1. 相机首帧应为 `source=640x480 input=yuv420-direct output=640x480`，
   编码前 `convert` 应接近零；实际 YUV420 帧为 460800 字节。
2. 比较原版的画面方向、颜色、视野、边缘、曝光及亮暗环境；抽样可能改变细节和
   抗混叠表现，不能仅以尺寸正确验收。
3. 两端移动画面并持续说话，记录每 30 秒 `status` 的音频溢出增量、转换耗时、
   视频接收/显示帧率及发送缓存；与 build.71 相同条件对比。
4. 重复摄像头开关、挂断重拨、设备/微信/H5 切换，确认 H5 恢复 1280×960，
   对讲恢复 VGA。持续通话和 AEC 双讲另行验收。

build.71 回退基线提交：`96a6dd3`。仅在上述实板验证完成后才能认定本实验有效。

## 2026-10-12 画质复查：原生 VGA 尚未验收

build.92 用户提供的微信上行截图在细线和高反差边缘出现彩色横纹；
build.93 改用 1280×960 采集、缩放到 VGA 后未见同样明显的横纹。
两次场景不同，也没有编码前原始帧，因此只能把问题缩小到采集/缩放路径，
不能据此认定 Bayer 顺序错误或某个寄存器已被证实有缺陷。

用户指定的旧版 Waveshare ESP32-P4 项目
没有原生 VGA 模式：`main/media/media_tuning.h` 选择 1280×960 采集，
`media_governor_make_rtc_av_policy()` 保留该采集尺寸，后续 PPA 做几何变换。
旧项目不能作为原生 VGA 正常工作的硬件证据。

OV5647 支持 VGA；Linux 驱动提供 binning 加 subsampling 的 VGA 模式。
但当前自定义模式只是沿用乐鑫 960p 的时钟和读出窗口，再改输出尺寸与步进。
源码对照发现，Linux VGA 与该组合还存在以下差异：

| 项目 | 当前自定义 VGA | Linux VGA 参考 |
| --- | --- | --- |
| `0x3820` | `0x01` | `0x41` |
| X 读出起止 | 24～2599 | 16～2607 |
| Y 读出起止 | 12～1943 | 0～1951 |
| `0x4004` 黑电平行数 | 4 | 2 |
| PLL、HTS/VTS | 沿用 24 MHz、960p/45 fps 配置 | 不同的时钟和 VGA 时序 |

这些是差异清单，不是应逐项照抄的修复清单。尤其 `0x3820` 高位在公开的
初版手册中标为测试用途，不能凭差异给它编造功能。跨平台参考的 PLL、MIPI
速率、曝光时基和 ISP 元数据必须成套验证，不能只复制 Linux 寄存器表。

参考来源：

- [Linux OV5647 驱动](https://github.com/torvalds/linux/blob/master/drivers/media/i2c/ov5647.c)：模式表和 VGA 几何/时序。
- [OV5647 初版数据手册镜像](https://wiki.geeetech.com/images/7/7e/Ov5647full.pdf)：第 3.2、4.1、4.2 节及系统时序寄存器定义。
- [Espressif OV5647 模式入口](https://github.com/espressif/esp-video-components/blob/master/esp_cam_sensor/sensors/ov5647/private_include/ov5647_settings.h)：检索时没有现成 VGA 表。

### 下一轮必须区分的三种现象

1. 彩条测试图也出现周期性错行或颜色错误：优先核查 Bayer 相位、CSI/ISP
   格式和帧布局。彩条通过只能验证其经过的链路，不能验证光学抽样质量。
2. 彩条正常，真实细线仅在 VGA 出现彩边：支持抽样混叠假设；并非简单调整
   H264 码率即可恢复。全幅 binning 后再缩放可能获得更好的细节和抗混叠表现。
3. 编码前图像正常，解码后才出现异常：再检查编码输入布局、缓存同步和压缩。

同一固定场景应比较黑白斜线、普通物体和彩色色块，固定光照、距离与对焦。
记录实际传感器模式、编码前 YUV、对应解码图以及帧率；保留 8 fps/256 kbps，
每轮仅改变一个诊断变量。原始用户媒体留在本地，不提交仓库。

本轮仅做文档/源码比较，没有修改驱动或生成新的修复固件；现有
`test_p4_native_vga.py` 覆盖格式协商、表引用生命周期与失败处理，
`test_full_frame_uplink.py` 覆盖采集策略，均不能判断真实传感器画质。
当前环境没有 `/dev/ttyACM*`，原始帧复现、VGA 画质和吞吐验收仍待实板完成。

### 2026-10-12 实板更新

后来已通过 `/dev/ttyACM0` 对同一 OV5647 场景抓取编码前帧。预热约一秒后，
原生 640×480 模式的两张 460800 字节 YUV420 图均出现强烈红蓝错边和彩色
条纹；1280×960 模式完整取景并以 CPU box 平均缩到 640×480 的首张对照图
没有对应异常。每张串口导出均按长度及 FNV32 完整校验。故障范围现可定位到
原生 VGA 的传感器/ISP 采集路径，不能再归咎于 H.264 码率；具体寄存器、
Bayer 相位或 ISP 配置原因尚未单独证明。产品默认继续使用全幅采集再缩小。
原始帧证据和通话性能的剩余验证见媒体诊断文档 build.98 小节。

### build.99 单寄存器对照

在 build.98 原生 VGA 编码前彩边与全幅缩小对照的基础上，build.99
恢复设备互呼/微信 VoIP 的原生 640×480 采集，并仅将自定义 VGA
模式的 `0x3820` 从基础模式的 `0x01` 改为 Linux VGA 表中的 `0x41`。
编码仍是 640×480、8 fps、256 kbps；H5 仍用 1280×960 原模式。
该高位在公开手册中标为测试用途，因此这只是受控试验，不能预设改善。
应先用空闲 `camera-snapshot capture-native` 对同一细线/高光场景抓原始帧，
再比较双机通话 `CAM` 的采集/转换耗时、`VRX` 的转换和呈现帧率，
以及音频溢出增量。若彩边仍在，回退到 build.98 或改用经画质验证的
全幅采集加硬件缩小路径。

用户确认 build.99 的彩边未解决。build.100 撤回该寄存器试验，设备互呼
改为 1280×960 全幅采集、PPA 完整缩到 320×240，以 15 fps、200 kbps
编码；这项对照主要检查
下行 QVGA 是否减少解码/显示负担，不能证明原生 VGA 问题已修复。
