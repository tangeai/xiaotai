# AI 对讲回复缺字：下行缓冲设计与试验依据

**决策状态：保留 beta.2 播放策略，先建立逐包对账和突发回放基线。** “你好，谢谢”中间漏听“好”是待定位现象。当前缺少对应板型、会话抓取和扬声器录音。本文用于决定下一轮试验，生产行为以[五板媒体契约](MEDIA_CONTRACT.md#五板-ai-下行自适应缓冲)为准。适用范围为 AI 回复下行。H5、设备呼叫、微信和多人对讲继续使用实时策略，声音识别的下载播放另有契约。

## 两个可复核的基线

当前基线是五板 `v1.2.0-beta.2`（`4dc2f93`，TiRTC 2.6.3）。默认 AI 下行是 16 kHz 单声道 Opus，按实际采样数累计待播时长。64 个压缩包槽和起播水位分别控制。目标初始 100 ms，范围 60–300 ms，断供后恢复至少 140 ms；有数据等待最多 400 ms，轮次结束可提前放行，结束后还有尾包到达窗口。AI 队列满时计数并拒绝新包，已接收部分按序播放。ESP 的待处理数包括入队预留和播放线程持有的槽，BK 的环计数在播放线程取走一包时减少。跨平台比较统一使用实际包、时间戳和已写采样数。

- [公共缓冲决策](../../platforms/common/include/xiaotai_audio_buffer.h)

参考版本为 xiaotai-esp32 v0.3.0（`f4161b3`）。它的 AI 模块请求 8 kHz G.711 A-law，以 20 ms 为名义包长，声明一次可到达 1000 ms 音频，媒体层默认另留 200 ms。变长记录按载荷、头部和对齐占字节环，容量计算还留回绕空间。两款 S3 的定时播放从 200 ms 起步；立创和 M5 的预填包数分别为 64 和 32，这两个值是启动条件之一，不能用作环容量。参考 P4 型号和尾音配置也与当前微雪 4.3C 不同。

- [参考 AI 模块](https://github.com/tangeai/xiaotai-esp32/blob/f4161b325e93a80f7b8077c53cd8dc0db5d5e994/sdk/modules/xiaotai_mod_ai_talk/src/ai_talk.c)
- [环与预算公式](https://github.com/tangeai/xiaotai-esp32/blob/f4161b325e93a80f7b8077c53cd8dc0db5d5e994/sdk/xiaotai_media/include/xiaotai/media_downlink.h)

同样是 1.2 秒，20 ms 包约需 60 槽，10 ms 包约需 120 槽。开始时已积压 20 包，紧接着到达 50 个 20 ms 包，若期间未消费，64 槽会拒绝 6 包，即 120 ms。稍后槽释放又能接收后续语音，听感可能是句中缺字。反过来，若队列曾经见底且所有包后来都成功写入，优先检查供给间隔与输出节奏。抬高起播水位会推迟首音，还可能让下一批到达前积压更多包。这个算例说明应分别测量容量与水位，不能用来判定现场根因。

## 五板内存账本

表中是 beta.2 构建的已知开销，单位 KiB = 1024 字节。ESP 在媒体初始化时在 PSRAM 分配连续接收池，AI 和实时接收复用该池。两款 BK 在启动 Opus 路径时动态分配 PSRAM 载荷环，另有静态数组。板载容量、空闲堆、最大连续可分配块要分开记录。

| 板卡 | 内存依据 | 64 槽基线 | 重点测量的竞争者 |
|---|---|---|---|
| 立创 ESP32-S3 | 板卡指南列 8 MB PSRAM | 64 × 1528 B = 95.5 KiB 接收池 | 摄像头 JPEG、上行预录、回声消除与显示 |
| M5Stack CoreS3-Lite | 8 MB Quad PSRAM | 同为 95.5 KiB | 显示、音频与网络并发时的内部 RAM、PSRAM 连续块 |
| 微雪 ESP32-P4 4.3C | 指南列 32 MB PSRAM | 64 × 1532 B = 95.75 KiB | 视频、显示缓冲、编解码任务栈和 DMA 内存 |
| 立创 BK7258 | 工程声明 16 MiB PSRAM、640 KiB SRAM，AP 动态堆仅为其中一部分 | 32 KiB 载荷，另有 2176 B 静态包长与时间记录 | AP/CP 两侧预算、AEC、工作栈、反复启停后的连续块 |
| 觅感 BK7258 | 物理 PSRAM 容量待核；须用本板运行数据 | 同为 32 KiB + 2176 B | 双屏 DMA、音频和会话切换；独立采样 |

ESP 每槽允许 1500 B 载荷，表内已含槽内元数据和对齐；空闲与就绪队列、队列控制块、分配器开销、解码工作区和 DMA 另计。BK 每槽载荷最多 512 B；表内两个静态数组分别为 128 B 和 2048 B，未含线程当前持包、PCM、Opus 状态和 AEC。

上述数值可在发布 ELF 上用目标 GDB 的 `p sizeof(audio_rx_item_t)` 或在 BK AP ELF 上用 `nm -S` 查 `s_opus_lengths`、`s_ai_packet_stamps` 复核。ESP 若改成 128 个固定槽，每块 S3 要再分配 95.5 KiB，P4 再分配 95.75 KiB，且整个新池需要连续空间；BK 再增 32 KiB 载荷及 2176 B 静态数组。不能从标称 PSRAM 推算出这些空间一定可用。

- [P4 接收池](../../firmware/esp-idf/esp32p4/waveshare-touch-lcd-43c/components/starter_media/src/starter_media.c)

### 怎样把账本用于选型

在同板、同 SDK、同录制条件下，把资源预算分为 PSRAM、内部可寻址 RAM 和 DMA 所需的内存能力。ESP 的内存能力可能重叠，不能把不同能力查询的空闲数相加。BK 分别采 AP 与 CP 的可用数据。每一类都记最小空闲量、分配前最大连续块、候选的常驻增量，以及合法业务切换时临时并存的最大需求。用同板多次基线最差值并留出观测波动余量；需要连续分配的对象还要逐个检查大小。仅有整机物理容量或单次空闲快照时，预算栏保持待测。分配失败应沿现有路径释放资源、留下失败阶段，避免大块载荷退回内部 RAM 挤占音频或 Wi-Fi。

| 硬件条件与实测结果 | 合理选择 |
|---|---|
| 五板基线对账完整，或异常在设备接收前已出现 | 保留固定槽和已有水位；先处理首次缺失所在环节。 |
| 两款 S3 确认小包挤满槽，内部 RAM 或最大连续块紧张 | 先离线回放等预算变长环。板上保留回调短路径，把环头、复制工作区和锁的成本一起算；分别在立创和 M5 验证。 |
| P4 在显示或视频切换时缺音，队列尚有余量 | 同步观察回调调度、解码耗时、DMA 写入与可用连续块。只有队列容量确实成为瓶颈才试增容；视频和音频按实际业务顺序切换。 |
| BK 的 Opus 环已满 | 先确定是突发、播放线程未及时运行，还是输出阻塞。保留已有缺口补偿、跨核时序和 AEC 参考；若变长环在锁内复制加重抖动，且本板 PSRAM 与静态区均有实测余量，可比较小幅增加固定槽的成本。觅感单独验证双屏同时刷新。 |

五板共用保序、可中断、有界等待的判断，差异仅限经验证的板级资源预算及平台存储适配。比较固定槽、等预算字节环、增容三种布局时，使用相同的到达序列和水位，分别报告每包拷贝次数、回调最长耗时、解码/写入耗时、栈最低水位及连续块。即使节省了容量，若额外复制和锁竞争使音频错过提交时刻，也不采用该布局。

## 决定做哪一种试验

| 现场证据 | 下一步 | 评价代价 |
|---|---|---|
| SDK 回调已有包，入队缺相同包，overflow 增长 | 对齐同一时刻的占槽、字节、待播毫秒和突发量。ESP 的有限次入队预留竞争也会计入 overflow；区分竞争与满槽后再决定是否扩容 | 预留竞争先查并发。满槽且小包居多，优先比较等内存字节环与当前固定槽 |
| 回放保序、无容量损失，出现断供和恢复 | 单独试调恢复水位或起播目标。比较缺音、首音和恢复延迟 | 过高水位会增加等待，尤其是一字回复；保留结束放行和 400 ms 等待边界 |
| 原始载荷完整，电脑和设备解码结果不同，或设备 PCM 完整而扬声器录音缺音 | 分别检查 Opus 解码、写入长度、硬件输出时序及打断/清空事件 | 此时扩容没有针对性；BK 的 PLC/FEC 补偿样本要单列，不能计为收到原包 |
| SDK 回调已缺段，或可见载荷在电脑独立解码也缺字 | 与服务端发送侧对账，核对轮次、流、媒体时间和原始载荷 | 设备侧仅能定位到最早可见边界；Opus 回调时间戳本身不足以证明网络丢包 |

**变长环作为有条件的候选。** 先用抓到的包长、媒体时长以及真实出队时刻回放，计算峰值活跃记录数、字节和毫秒。按候选格式逐条累加“对齐后的载荷 + 记录头”，另计最大记录的回绕余量、消费端持有的包、索引、同步和必要复制。保留各平台原最大合法包；还要限制记录数和待播时长，以免极小包或长句积压拖慢打断。1.2 秒仅作为可对比的首组输入。用最短包、高码率包和未排空的连续突发检验边界，不能用平均码率承诺零丢包。

首轮以**同板基线接收内存为上限**，比较总量、各内存区域和最大单笔分配；采用新布局时应替代原存储，避免两个完整池同时驻留。只有等内存方案仍失败、且已量出具体板卡余量时，再单变量试验增加预算。SDK 回调保持有界、无逐包分配或阻塞等待；设计需验证并发生产者、回绕中途复位、会话代次切换、读者持包和失败归还。若对象结构变动，回归共享池的实时业务，沿用原来的低延迟和淘汰策略。共用业务决策，板级只选择可证实的资源预算。

## 可独立借鉴的验证工具

参考仓库按芯片和 ESP-IDF 版本校验 TiRTC 官方包的哈希、头文件和 ABI。后续若升级 SDK，建议把这些检查加在构建机上，并把包标识写入实验记录；它们不占设备运行内存。当前五板已链接 2.6.3，比较缓冲实现时应固定同一 SDK，避免两项变化混在一起。[参考 SDK 契约工具](https://github.com/tangeai/xiaotai-esp32/blob/f4161b325e93a80f7b8077c53cd8dc0db5d5e994/scripts/tirtc_contract.py)

参考仓库的真实 LVGL 主机预览适合单独验证字幕、房间页和字形。预览运行在电脑上，可用于排除视觉缺字；扬声器播放连续性与屏幕负载造成的调度延迟仍需板上测量。此次排查可同时记录字幕与实际听到的语音，避免混淆两种现象。[参考 UI 预览工具](https://github.com/tangeai/xiaotai-esp32/blob/f4161b325e93a80f7b8077c53cd8dc0db5d5e994/tools/ui_preview.py)

## 验证顺序与采用条件

1. **建立同板基线。** 记录板型、固件构建号、SDK、会话代次、包格式及复现原话。分别在启动后、媒体初始化后、AI 播放峰值、打断/切换通话、结束回收后取样。记录内部 RAM、PSRAM 的空闲值/最低值和最大连续块，另记 DMA 可用块、音频任务栈最低余量、回调与写入耗时。BK 分 AP/CP，无法取得的指标标明缺测。S3 深度抓取会额外占用最多约 256 KiB 音频与约 160 KiB 追踪空间；诊断固件用于对账，资源结论用关闭抓取的同配置复测。
2. **定位第一次不一致。** ESP 会话摘要的 `rx` 是成功入队数。结合回调、入队、出队、成功写入和扬声器录音，按流、代次、时间戳、载荷指纹核对。调试抓取有界，检查完整性和丢记录数；只在操作、结束或异常时输出摘要。S3 可同时比较 `host-opus.wav` 和 `device.wav`，其拼接结果不含硬件播放间隙。BK 结合 `peak / slots / queued-ms / underruns / plc-ms`；缺少某阶段证据时保留待定。[现有抓取步骤](../development/MEDIA_PIPELINE_DIAGNOSTICS.md)
3. **回放后再改参数。** 固定语料和到达序列，以 50 × 20 ms 为第一批，覆盖十批连续突发、已有积压后提前到达、10/20 ms 混合、队列和字节边界、单包短句、供给中断、晚尾包、主动打断和 AI → 通话 → AI。每个输入包有可核对的序号；无需网络即可确定首次丢失位置。并发回放校验槽归属及旧代次隔离。先让当前实现对现场失败样本给出相同结果，再比较候选。[参考突发回放](https://github.com/tangeai/xiaotai-esp32/blob/f4161b325e93a80f7b8077c53cd8dc0db5d5e994/sdk/xiaotai_media/test/downlink_test.c)
4. **采用或回退。** 确认在声明容量内零新增丢包、零乱序、零跨轮次音频；超预算时保留已收前段并准确计数；播放开始后不为追水位主动停播。比较同板同场景首音及恢复延迟的中位数、P95、最大值，记录样本数。首轮以现行等待边界和基线分布为参照，候选允许的延迟增量、分区最低余量和测试轮数在试验前登记。若资源余量缺测、出现分配失败、实时通话退化或连续启停无法回到基线范围，保留现行实现。变更共用策略时，五板均运行同一行为回放、原生构建及各自的硬件验证。单板结果只覆盖该板。[跨板回放](../../tools/tests/test_media_queue_policy.py) · [ESP 播放边界](../../tools/tests/test_esp_ai_playout.py)

每轮在本地忽略目录 `tests/.local/` 保存录音、追踪、构建身份与原始计数。长期保留的结论按下表追加，记录通过、失败或缺测；只有经验证并采用的行为才同步至媒体契约。
