# P4 设备互呼性能优化记录

## 当前产品基线

设备互呼以 H.264 640×480、5 fps、目标 600 kbps 为基线；
保持 1280×960 完整取景采集、640×480 等比例显示及现有旋转功能。
8 fps 尚未作为稳定档位验收。5 fps 是配置目标，旋转负载下实际显示可能低于目标，
具体实测限制见下文；后续优化以此版本作对照，不将其标记为性能问题全部解决。
微信配置继续保持 down_video_rotation=0 与 P4 cw90，不随设备互呼基线调整。

## 2026-10-07：减少旋转画面的无效 CPU 访存

状态：代码和主机测试通过，固件编译通过；收到双机实测日志，局部改善迹象成立，
但严格 A/B 对照不足，旋转后的双向并发压力尚未解决。
保持 1280×960 完整取景、640×480@5 编码、640×480 显示画布和微信 0+cw90。

### 本次改动及可验证收益

- 原来有黑边时清零整个画布，改为仅清零实际视频矩形之外的区域。
- 原来交换整个画布的 RGB565 字节，改为仅交换实际视频区域；黑色不需要交换。
- 保留缓存同步和缓冲区生命周期，不假设上次画面布局相同，避免旋转后残影。
- 处理奇数偏移和步长，避免未对齐的 32 位访问。
- 修正性能分析脚本：接受包含 `adapt=0/1` 的紧凑日志，并保留平均排队字段。

640×480 画布内显示 360×480 竖画面时，按代码访问范围计算：

| 操作 | 改前 | 改后 |
| --- | --- | --- |
| 黑边准备的 CPU 写入 | 614400 字节/帧 | 268800 字节/帧 |
| 字节交换覆盖范围 | 614400 字节/帧 | 345600 字节/帧 |

这里只是逻辑访问量，不包含缓存行放大、缓存维护、PPA、解码或显示传输，
不能换算成延迟下降百分比。0° 完整铺满画布时主要路径的访问量基本不变。
PPA 的 `byte_swap` 是输入侧功能，不能直接代替 YUV→RGB565 的输出字节交换。

### 实机验证及判定

当前环境没有串口设备，烧录和以下实机日志由用户提供。
两台设备更新后保持相同位置和光照，分别固定 0°、270° 各通话 60 秒，丢弃启动
10 秒的统计。记录双方完整 ELF 身份以及 CAM/VRX 行；避免统计窗口内切角度。
按相近接收码率比较 pack、swap、总转换、显示 fps、平均排队和丢帧。
确认完整取景、颜色、黑边、旋转恢复、双向声音和重复挂断/重呼都正常。

分析保存的日志：

```bash
python3 firmware/esp-idf/esp32p4/waveshare-touch-lcd-43c/tools/analyze_media_performance.py --help
```

有效：匹配场景下转换/排队降低，显示帧率不下降、声音和画面无回退。
若只是码率变低或角度不同，记为“对照不足”；若耗时未降，记为“实机未见收益”，
继续测调度/带宽，不以指令或访问量减少代替实测结论。

### 双机日志回收结果（2026-10-07）

A 为 IP 尾号 .84，B 为 .246。A 启动 ELF 前缀 `f741a7b98` 与本次产物一致；
B 提供的片段没有应用身份行，不能独立核验其完整 ELF。两台 uptime 不同步，
通过房间 ID 对齐：第一通双方保持 0°，第二通双方在开始后切到 270°。
第二通第一条 VRX 含切角过程，排除；第一通也排除第一条 VRX。
以下为剩余窗口等权平均，不是逐帧加权平均，也不是端到端延迟。

| 设备/角度 | uptime 区间 ms | 窗口数 | 显示 fps | 转换 ms | pack ms | swap ms |
| --- | --- | --- | --- | --- | --- | --- |
| A / 0° | 462031–562671 | 11 | 4.93 | 102.4 | 42.2 | 18.7 |
| B / 0° | 465429–566309 | 11 | 4.84 | 152.3 | 76.5 | 22.6 |
| A / 270° | 599517–770766 | 18 | 4.59 | 179.2 | 109.0 | 11.1 |
| B / 270° | 602738–774377 | 18 | 4.81 | 133.1 | 81.3 | 11.3 |

判定与限制：

- 两台旋转后的 swap 均约 11 ms，与减少交换范围的预期相符。B 的 270°
  转换窗口为 92–173 ms，旧 .246 样本为 172–196 ms；有改善迹象，但旧样本
  固件身份不完整、场景不受控，不能据此宣布确定的收益百分比。
- 0° 与 270° 来自不同通话，输入码率也不同，不能把表中差值全归因于旋转。
  尤其 A 第一通输入约 333–561 kbps，第二通稳定窗口约 373–623 kbps。
- A 的 270° 转换仍接近 200 ms 帧间隔，显示仅 4.3–4.8 fps；B 为 4.7–4.9 fps。
  A 上行缩放同时从第一通约 64–69 ms 增至第二通约 83–110 ms，最大出帧
  间隔约 276–331 ms，多次 drain=1；B 第二通缩放约 66–71 ms，drain=0。
  这提示整条双向流水线的并发资源争用值得优先检查，尚不能区分 CPU 抢占、
  PSRAM 带宽与 PPA 等待，更不能只认定是旋转算法本身。
- 两台没有解码失败、解码重置或输入溢出记录；仍有转换阶段丢帧。
  排队字段不是摄像头到屏幕的端到端延迟，队列浅不代表没有可感知延迟。
- 初次 40202 后 cleanup confirmed，重拨成功；第一次挂断后再次双向建连成功。
  SDK 头文件将 -40008 定义为远端主动关闭，这些退出附近对端也有挂断记录，
  不应当作之前 -40007 心跳超时复发。异常断网清理仍需单独故障注入验证。
- A 启动 SNTP 超时后重试成功，并有 already initialized 提示；属于另外的启动
  重试问题，不是本次持续通话性能结论的依据。

取景来掩盖压力。颜色、完整取景、旋转恢复、双向声音需人工确认，日志不能替代。
